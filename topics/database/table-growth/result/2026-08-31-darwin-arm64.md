# Table growth results

These are local observations from the first version of the experiment. They are included to make the README's claims reproducible, not as universal performance numbers.

## Environment

- Date: 2026-08-31
- Platform: macOS Darwin arm64
- SQLite: 3.51.0
- Command: `python3 topics/database/table-growth/benchmark/run.py --rows 100000 --json`
- Command: `python3 topics/database/table-growth/benchmark/run.py --rows 1000000 --json`
- Each query was warmed five times; the reported value is the median of 200 lookup samples or 30 pagination samples.

## Observations

Median query time in microseconds:

| Rows | Lookup, no index | Lookup, indexed | Deep `OFFSET` | Deep cursor |
| ---: | ---: | ---: | ---: | ---: |
| 100,000 | 3436.9 | 64.3 | 357.0 | 44.5 |
| 1,000,000 | 34941.9 | 41.5 | 5748.6 | 17.4 |

The no-index lookup grew from about 3.4 ms to 34.9 ms as the table became ten times larger. The indexed lookup stayed in the same rough range in this run because it visits the matching index entries rather than scanning every row.

The deep page was selected near the end of each table: offset 99,000 for 100,000 rows and offset 999,000 for 1,000,000 rows. `OFFSET` became substantially slower because the engine still walks past the skipped index entries. The cursor query starts at the supplied ordered key and did not pay that same skip cost.

The plans reported by SQLite were:

- No-index lookup: `SCAN orders`
- Indexed lookup: `SEARCH orders USING INDEX orders_customer_id (customer_id=?)`
- Offset pagination: `SCAN orders USING COVERING INDEX orders_created_id`
- Cursor pagination: `SEARCH orders USING COVERING INDEX orders_created_id (created_at>?)`

## Caveats

- This is SQLite on one laptop, with a warm process and no competing workload.
- The lookup's `customer_id` distribution, payload width, and returned row count are fixed by the script.
- The cursor case uses an ordered, monotonic `(created_at, id)` key. A cursor design must account for ties and changes to the ordering columns.
- The benchmark does not measure index-build time, insert/update cost, storage size, locking, network latency, or server-side buffer-pool behavior.
