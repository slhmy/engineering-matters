# Result: 2026-08-23 darwin/arm64

This result is one local observation from an Apple M4. It compares four local shard counts and `orcaman/concurrent-map/v2`; use it to compare trend shape, not as a universal performance claim.

If the allocation column shows three `B/op` values, the format is `-cpu=1/-cpu=4/-cpu=8`.

## Environment

- Date: 2026-08-23
- System: darwin/arm64, Apple M4
- Go: go1.26.6
- Command:

```bash
cd topics/go/sync-map/benchmark
go test -bench=. -benchmem -benchtime=1s -cpu=1,4,8
```

Observations:

- With uniformly distributed writes, `sync.Map` remains competitive at eight CPUs because updates can use different parts of the hash trie.
- With uniformly distributed keys, increasing the local shard count generally reduces write contention: `shard4` reaches 80.57 ns/op at eight CPUs in the 100% write case, compared with 22.05 ns/op for `shard128`.
- With 10 hot keys, `sync.Map` falls behind the sharded implementations at eight CPUs, although it remains ahead of the single global locks in this run.

- With one hot key, changing from 4 to 128 shards has little effect because all writes still use one shard.
- The single-hot-key workload makes `sync.Map` slower at eight CPUs than at one CPU, showing that extra goroutines cannot help when all writes target one contended location.

## Local Conclusions

This run supports a few small conclusions:

- `sync.Map` remains a strong choice for stable-key, read-heavy workloads under concurrent reads.
- `map + lock` is still cheap on one CPU, so the extra machinery of `sync.Map` is not automatically worthwhile at low concurrency.
- For write-heavy or continuously growing key sets, sharded maps are competitive and report fewer allocation events than `sync.Map` in this benchmark.
- More shards help distributed writes but do not solve a single hot-key bottleneck; they also add memory and lock-management overhead.
- Write-heavy performance depends on key contention, not only on the write ratio. `sync.Map` handles distributed writes better than single-hot-key writes.
- These numbers describe one Apple M4 run with Go 1.26.6. Repeat the experiment on the target machine and workload before using the result to choose an implementation.
